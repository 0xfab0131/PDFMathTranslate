# 1. 安定版 Docker イメージで発生した例外の構造整理

## この文書の役割

この文書は、今回観測された例外を、

1. 画面に最後に見えた例外
2. その手前で起きていた可能性が高い一次障害
3. 設定不足で説明できる部分
4. 実装の制御上の欠陥として切り分けるべき部分

に分解して整理するための補助文書です。

今回の依頼の中心は「コードを直すこと」ではなく、「安定版 `Docker image` をローカルで適切に構成し、何をどう設定すればよいかを正確に理解すること」にあります。  
そのため、ここでは修正案より先に、失敗の意味を厳密に整理します。

---

## まず結論

今回 UI 上で見えている

`UnboundLocalError: cannot access local variable 'file_mono' where it is not associated with a value`

は、そのまま一次障害そのものだとみなすべきではありません。

本質的には、次の二段構造で考えるのが妥当です。

- 第一段: 何らかの理由で、実験的な `BabelDOC` 系翻訳処理が正常な `finish` 経路に到達していない。
- 第二段: それにもかかわらず GUI 側が `file_mono` を返そうとしてしまい、二次例外として `UnboundLocalError` を出している。

したがって、今回の現象は単純に

- 「環境変数が足りない」
- 「API key を入れれば直る」
- 「Docker の起動方法だけが悪い」

と断定できるものではありません。

特に今回の UI 上の選択は `Service = Bing` であり、これは少なくとも `OpenAI` 系のような API key 必須サービスではありません。  
したがって、今回の失敗を最初から「認証情報不足」とだけみなすのは、構造的に粗いです。

---

## 今回観測された事実

今回の事実として整理できるのは次の通りです。

- 使用しているのは OSS の安定版 `Docker image` `byaidu/pdf2zh`
- 起動方法は、README の最小例に近い素の `docker pull` と `docker run -d -p 7860:7860 ...`
- GUI には PDF を渡している
- GUI 上では `Service = Bing`、`Translate to = Japanese`
- 実験的経路として `Use BabelDOC` が見えている
- 進捗は `Parse Page Layout (Complete)` まで進んでいる
- 最後に `pdf2zh/gui.py` 内で `file_mono` 未代入の例外が出ている

この時点で既に分かる重要点は、少なくとも

- 入力 PDF の受理
- GUI から翻訳処理への突入
- レイアウト解析フェーズの進行

までは到達しているということです。

つまり、完全に初期化以前で即死しているわけではありません。

---

## 三つの層を分けて考える必要がある

今回の調査では、同じ `PDFMathTranslate` という名前の下に、少なくとも次の三層が混在しています。

| 層 | 実体 | 今回どう扱うべきか |
| --- | --- | --- |
| A | 現在手元で動かしている安定版 `byaidu/pdf2zh` イメージ | 主対象 |
| B | 現在の root リポジトリ `main` の実装と README | 参照対象。ただし Docker Hub 上の image と完全一致とは限らない |
| C | `pdf2zh/kernel/PDFMathTranslate-next.git` 以下の `next` / `v2` 系資料 | 別系統。機能理解には有益だが、安定版 image と混同してはいけない |

この区別が重要なのは、現在の root 実装では GUI が `Translation Mode = fast / precise` へ寄っている一方、実際にユーザーが見ている GUI には `Use BabelDOC` という別の表現が残っているからです。

このズレは、

- Docker Hub の配布 image とローカル checkout のソースが完全一致しない
- 同じ `1.9.11` 表示でも UI 構成が既に移行途中である
- 実験的経路だけが古い設計を残している

といった可能性を示唆します。

したがって、「今画面で見えているもの」を絶対視せず、  
「安定版 image の利用方法」と「現行 main / next docs の設計意図」を分けて整理するのが本質的です。

---

## 例外の構造

root 実装の `pdf2zh/gui.py` には `babeldoc_translate_file()` があり、その内部の `yadt_translate_coro()` では、`event["type"] == "finish"` のときにのみ `file_mono` と `file_dual` が代入されます。

ところが、その `finish` を経ないまま関数末尾へ到達すると、最後に

- `str(file_mono)`
- `str(file_dual)`

を返そうとして `UnboundLocalError` になります。

つまり、この例外は

- 「翻訳が最後まで成功した」ことを意味しない
- 「翻訳処理が別の理由で終了した」か
- 「正常終了イベントを GUI 側が受け取れていない」

ことをむしろ示しています。

言い換えると、今回画面で見えている例外は「真犯人」ではなく、「真犯人が見えにくい実装経路の上に現れた二次破綻」です。

---

## 一次障害候補は何か

今回の情報だけから一意に断定はできませんが、一次障害候補は大きく次の群に分かれます。

### 1. 実験的 `BabelDOC` 経路そのものの不安定さ

今回もっとも重要なのはここです。

安定版 `byaidu/pdf2zh` の中で `BabelDOC` は README 上でも

- `Experimental backend`
- `--babeldoc`
- 近年は `--mode precise` へ移行中

という扱いです。

したがって、

- 安定版 image の「標準運用経路」
- 実験的 `BabelDOC` 経路

を同一レベルの安定性で見てはいけません。

今回のように、`Parse Page Layout` まで進んだ後で `finish` を返せないという現象は、まさにこの実験経路の境界条件で起きやすいタイプの不整合です。

### 2. レイアウト解析モデルやその周辺資産へのアクセス問題

README には `DocLayout-YOLO` の取得に関するネットワーク注意があり、`HF_ENDPOINT` によるミラー設定も案内されています。

したがって、もし実行中 image が事前に十分 warmup 済みでない場合には、

- モデル取得
- モデル読込
- その途中のネットワークやキャッシュ

が一次障害になり得ます。

ただし、今回のようにかなり進捗が進んでいる場合には、単純な「起動時にモデルが無い」だけでは説明しきれない可能性もあります。

### 3. PDF の構造と実験経路の相性

対象は論文 PDF であり、しかも今回の目的は数式やレイアウト保持です。  
この種の文書では、

- 多段組
- 図表
- 複雑な数式ボックス
- OCR っぽいページ
- フォント情報の揺らぎ

などがレイアウト解析・再合成に強く影響します。

そのため、一般のテキスト中心 PDF では起きない不整合が、実験的経路では顕在化しやすいです。

### 4. 外部翻訳サービスよりも前段の問題

今回 `Service = Bing` なので、少なくとも

- `OPENAI_API_KEY`
- `GROK_API_KEY`
- `DEEPL_AUTH_KEY`

のような認証情報不足は、今回の第一候補ではありません。

もちろん Bing 側通信の問題はあり得ますが、今回の進行状況を見る限り、まずは前段のレイアウト・実験経路の制御を疑う方が自然です。

## 今回の失敗を「設定不足だけ」で説明しない方がよい理由

今回の依頼の本質は「適切な構成を組むこと」ですが、その前提として次の認識が必要です。

- 構成を適切にしても、実験的経路の制御欠陥は消えない
- 逆に、実装に欠陥があっても、標準経路を使えば現実的な運用は可能である

この二つを混同すると、

- 本来は避けるべき experimental path を設定で何とかしようとして消耗する
- 安定版 image の標準運用を先に固めるべきなのに、いきなり複雑な経路へ進んでしまう

という誤った順序になりやすいです。

今回本当に価値があるのは、

1. 安定版 image の標準運用を先に成立させる
2. その上で必要に応じて API/proxy/Ollama 連携を導入する
3. さらに必要なら `BabelDOC` / `precise` / `next` を別レーンとして扱う

という層構造で理解することです。

---

## 今回の依頼に対する運用上の意味

今回の障害整理から、手順書には次の原則を必ず反映すべきです。

### 原則 1

`docker run -d -p 7860:7860 byaidu/pdf2zh` だけで「すぐ全部安定して使える」とは見なさない。

最小起動は出来ても、

- 設定の永続化
- cache の永続化
- 出力ファイルの保持
- 外部サービス接続
- 実験的経路の扱い

は別問題です。

### 原則 2

安定版 image では、まず experimental な `BabelDOC` 経路を切り離して標準経路を確認する。

### 原則 3

`config.json` と `cache` の保存先を、コンテナ外に意識的に持たせる設計が重要である。

### 原則 4

`next` / `v2` 系ドキュメントは有益だが、現在の stable image と 1 対 1 に対応すると仮定しない。

---

## この文書から次へ進むための要点

次の文書では、今回の障害分析を前提として、

- どの設定面があり
- それぞれがどこに保存され
- Docker ローカル運用では何を volume 化し
- どのサービスをどう接続し
- どの範囲までを stable v1 の責務として扱うべきか

を体系化します。

要するに、今回の失敗は「設定をちゃんと設計しよう」という方向性自体は正しい一方で、  
同時に「実験経路の失敗を、設定不足だけに還元してはいけない」ということを教えています。
